## Step 1. NEES on the persistent path (objects_live14fixA, objects_live15birth)

### What was run
- The brief's command, `nees_agents.py <run> <run>`, prints an empty table for these two runs. Two reasons:
  - Both runs are two legs with no dwell. `legs.tsv` windows (arrival to next leg) are 4 to 5 s, and the script trims 3 s and needs 10 samples, so no room fit exists.
  - Neither run has `c3a_instances.csv` (it needs `ltom_repertory_end.json`, which these runs do not have), so no node is matched to a Webots object.
- So I wrote `tools/step0/nees_persistent.py`. It keeps the chain of `nees_agents.py` and changes only how rooms and matches are found.
  - Chain: Webots world, then room_concept's internal frame by a rigid fit per room, then the published frame by the logged gauge at the row's time.
  - NEES = e^T P^-1 e with the agent's own diagonal sigma (`std_cx`, `std_cy` of `<class>_ai2_log.csv`), divided by 2 DOF.
  - Room membership comes from the ground-truth position inside the Webots room polygon (`wbt_rooms.rooms()`), not from `legs.tsv`. The fit uses every sample inside the polygon after the first 3 s.
  - Node to object: each row is mapped back to the world; the match is the nearest Webots object of the node's class within the c3a radius (nightstand 0.5 m, bed 1.2 m), and that object must lie in the room being visited.
- World: the live file `webots-shadow/worlds/piso/threerooms-piso.wbt`. It was last modified 2026-11-22 19:29 (git has it modified, uncommitted). The runs started 21:31 and 22:12, so it is the world they ran in.
- Room names here are the polygon names of `wbt_rooms.py`, not the graph's `room_N`.
- Builds: live14fixA ran cost-removal `50bfcee7` agents; live15birth ran `014112c3` (from `agents.txt`).
- Both runs hold only one visit per room, so every row is a first visit. No toilet log exists in either run (toilet is Step 2).

## Step 3. Claim-refusal cause (G6)

### Searched
- Runs: c3a_1, c3a_2, c3a_3, c3a_cab1, c3b_on1, c3b_off1, c3b_on_hidden1, c3b_off_hidden1, c3b_on_ltom1, c3b_off_ltom1 (the ones in `auro_1122/nees_summary.md`), under `room_concept/estimation_scripts/crossing/`.
- Pattern: `STOPPED TARGET REFUSED` in `<run>/logs/controller.log`. This is the controller's `[why]` line when a claim ends refused. Other `REFUSED` lines are `[footprint] yaw-correction monitor` statistics and `MOVING ... was TARGET REFUSED` follow-ups, not new refusals.
- Result: 55 refusals (c3a_1 15, c3a_2 4, c3a_3 11, c3a_cab1 9, c3b_on1 4, c3b_off1 7, c3b_on_hidden1 1, c3b_off_hidden1 1, c3b_on_ltom1 2, c3b_off_ltom1 1).
- The log has no timestamps. I turned each line number into a time with the `controller` column of `gt_pose.tsv` (controller.log line count, about 1 Hz). The robot position then comes from `proto_room.csv` (internal x, y) and the logged gauge to the published frame. The standpoint is the `at (x,y)` in the line. Script: `tools/step0/refusals.py`.
- `slam_shadow.csv` holds the SLAM and SDF estimates in the internal frame; I used the room_concept pose in `proto_room.csv`, which is the same estimate and carries the gauge.
- The robot footprint is the circumscribed circle, radius 0.3249 m (`ROBOT_GEOMETRY.md`, maximum support radius at -52 deg).

### By cause
| cause | n | what the log says |
|---|---|---|
| standpoint inside the robot footprint | 6 | refused with the robot within 0.3249 m of the standpoint (0.09, 0.09, 0.13, 0.21, 0.22, 0.32 m) |
| occupied cell, or wall, object, residual cell under the body | 44 | refused with the robot more than 0.3249 m away. The controller does not say which kind of cell; see below |
| no route (`afford_room`, not an object standpoint) | 5 | "no route from here, and no closer pose the robot can reach" |
| total | 55 | |

Of the 50 occupancy-belief refusals, the distance robot to standpoint is 0.09 to 6.47 m, median 1.75 m.

### What could not be split
- The occupancy text is one message for three things: "a wall, object or unbelieved residual cell lies under the body in the turn it ends with at the published standpoint" (`controller_session.cpp:1921`). The log does not separate wall, object and residual.
- The `residual_concept` `grid` node is in every `graph_trace.csv`, but only as `node_insert` / `node_delete` and a `parent` attribute. No cell content is in the trace. So "occupied cell" cannot be checked against the grid, and the 44 stay together.
- `standpoint_audit.jsonl` (the controller's own audit file) is not in any of these run dirs.

### Caveats
- Time and robot position have about 1 s resolution (and therefore up to about 0.3 m of motion), so the footprint test is soft near 0.3249 m. The 0.32 m case could fall either side.
- Some refusals repeat the same target (for example `aff_chair_98` four times in c3a_1). They are counted per refusal line, not per target.
- Names starting `aff_door`, `aff_door_look_place` are counted with the object standpoints, as the controller does (they take the same branch).
- This is not the cause of the 18 zero-update windows in `claim_windows.md`; it is only the cause split for refusals.

A positive offset means the mask edge is outside the graded silhouette (the mask is bigger); negative means inside.

### How far to trust these numbers
- They are upper bounds on the sensor's boundary error. The tool compares the mask with the box, and three other differences are inside the number: occlusion (the mask is the visible part only), the box being bigger than the real object (a box hull over a toilet's bowl and tank), and the mask covering more than the graded layer (the bed mask takes in frame, blanket and pillows, the mattress box does not; the table box includes legs).
- That is why the mean offsets are far from zero: nightstand -12.9 px, toilet -19.5 px (masks smaller than the box), bed +24 px (mask larger than the mattress). A pure sensor error would centre near 0.
- The refrigerator is the cleanest case: a single box-like body, mean offset -0.6 px, sigma_px_boundary 4.5 px, residual std 5.0 px, eps_px 0.066. If one value is taken as the sensor's boundary error, it should be this one, with the others as the ceiling.
- sigma_px_boundary here is the std over frames of the per-frame mean. A constant layer mismatch moves the mean (not shown in sigma), but a mismatch that changes with view angle and range shows up in sigma.

### Pixels or metres?
Frames binned by range z (the box centre's depth along the optical axis) into 4 equal-count bins, so no cut-point was chosen. Each bin gives the mean |per-frame mean offset| in px and the same in metres, |offset| z / f. The slope b is the log-log slope of |offset| against z over frames, with a bootstrap 95% interval (2000 resamples of frames). b = 0 means constant in pixels; b = -1 means constant in metres.

Conclusion:
- Neither form is flat across classes.
  - Nightstand, toilet and table fall with range; in the nightstand and toilet the metres column is close to flat.
  - The bed rises with range.
  - The fridge cannot decide (interval contains 0 and -1).
- Pixels are not flat in any class whose slope is determined: the interval for b excludes 0 in the nightstand, toilet, table and bed.
- So `camera_shared_var = (sigma_px z / f)^2` (an offset constant in pixels, turned into metres) is not supported. What the data show for the classes with a clear fall is an offset that is nearly constant in metres at the object.
- Caution on this reading: a constant offset in metres is exactly what a fixed layer mismatch would produce (a box bigger than the object, a mask that omits a part), so the 'flat in metres' result for the nightstand and toilet may be geometry, not the sensor. The classes where the layer mismatch is smallest (the fridge) have an undetermined slope. This measurement does not separate the two. It rules out a pixel-constant offset for the classes that have one measured; it does not show that the sensor error is constant in metres.

## Step 5. Latency
Sources, all from this run (epoch 1795479562, 2026-11-24 01:19 CET):

| quantity | value | n frames | source |
|---|---|---|---|
| tau_cam_s (capture stamp minus newest pose stamp, as logged: `rt_lag_s`) | median 0.000 s; mean -0.002 s; 5%/25%/75%/95% = -0.043 / -0.016 / +0.019 / +0.034 s; 43% of frames negative | 1252 of the 1356 dumped frames | `retina/etc/mask_motion_log.csv`, column `rt_lag_s`, matched to the dump's frame stamps by `ts_ms` |
| tau_lidar_s | not measurable from this run's logs (see below) | | |

- Definition of the column (`retina/src/graph_publisher.cpp` lines 405-426): for each ZED frame, `rt_lag_s = frame_ts_ms - newest stamp in the robot->room RT edge's `rt_timestamps` ring`. A positive value means the newest pose is older than the image; negative means the pose is newer than the capture. The brief's tau is pose stamp used minus capture stamp, which is the negative of this column; its median is also 0.0 s.
- The 104 dumped frames with no row in `mask_motion_log.csv` (no masks in that frame, so no log row) are left out.
- The value is not a latency of the pose chain: the pose ring is dense (median spacing between the two newest stamps 0.055 s over the file), and the retina picks the newest stamp, so the lag is within the ring spacing. The spread (+-0.04 s) is that spacing. The pose actually used for a mask is interpolated or extrapolated to the capture stamp (`MaskMotion.pose_extrapolate`), so a median of 0 says that this stamp is aligned, not that the pose arrived with zero delay.
- Not found: the countable agents' `<class>_ai2_log.csv` have `pkt_ts` (the capture stamp of the packet) but no stamp of the pose used. So the brief's column pair does not exist there.
- Lidar: no log of this run holds a lidar sweep stamp next to a pose stamp. `ai2_log` columns have no stamp except `pkt_ts` (the packet's own stamp, which for the lidar path is the same field), and `room_concept` and `retina` logs have no lag line for it. The only lidar-age number is the controller's `returns_age_s` in `controller/policy_decisions.csv` (median 0.003 s, 2445 rows), which is the age of the returns when the controller reads them, not capture-to-pose. So tau_lidar needs a new log column (pose stamp used per sweep) before it can be measured. The file starts inside this run (first stamp 1795479580131).
