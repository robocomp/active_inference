# Review: joint calibration r2 — kinematic factor, floor, verticals (+ Task 1b odometry-readiness) — Fable, 2026-10-08, read-only

## Summary in plain words

1. The kinematic rows are the right idea and the live logs confirm them, but one sign is backwards: a sensor planted +1° CCW produces a POSITIVE coefficient of the lateral innovation on forward travel in every planted log (+0.81°, +0.92°; null +0.03°), so the yaw row must read +ψ·d_fwd if ψ is "the helios yaw the localiser adds to the heading". Written as −ψ·d_fwd the estimator returns −ψ and the signed Task 6 grade fails for a working estimator. Also, because the innovation is expressed at the MIDPOINT heading, the (1−cos) columns do not exist; the lever regressor is 2·sin(dθ/2) on the cross-axes only.
2. The odometry-readiness policy (Task 1b) has the right instinct but the wrong shape: an odometry-parameter error is the SAME on every row, so it biases the mount coherently; adding it as a per-row variance makes it (0.4 mm)² against (4–6 mm)² rows and changes nothing. Marginalise it as a shared nuisance (the Woodbury/Schur common-mode this project already uses) with the calibrator's posterior + drift as its prior. That is still decoupled (the odometry is never re-estimated by the mount factor), it reproduces the user's "wait until stable" behaviour by weight, and the re-referencing term (4) falls out of the same cross-information for free. In the logs as driven (turns in both directions) the forward-scale/lever correlation is ≈ 0, so this is insurance, not the cause of the 20–35 % lever shortfall (19–27 mm recovered vs 30), which remains unexplained and must be looked at before it is graded.
3. The floor factor is sound; two frame facts must be pinned: the points are in the Shadow frame (origin on the floor), so z_true = 0 is right but the bpearl origin is at z = 0.7025 there, not 0.67; and a body-frame rotation about the sensor origin is the right estimation convention for the INVERTED sensor, but writing it back to shadow.json flips the roll and yaw signs (R_err·Ry(π) = Ry(π)·R'), so the write-back must compose, not add.
4. The vertical factor has one trap that would silently defeat the whole plan: the helios's own planar residual against the map it built is zero by construction, and with the "localiser's own covariance" (10 mm) as the per-sweep nuisance prior the Schur complement leaves a false "dx = 0" measurement worth (10 mm)⁻² per sweep — thousands of sweeps would crush the kinematic factor's 30 mm. Drop the helios planar rows outright and give the nuisance a wide prior (the pose-field σ, not the solver's claim). Also the map walls sit where the helios TILT put them at the 1.5–2.0 m band, so the bpearl's "relative planar offset" absorbs 0.67 m × helios tilt (8 mm per 0.7°): add that coupling or the helios-tilt arm moves the bpearl.
5. Gauges are consistent (helios z honestly unanchored; floor = z 0; everything else relative to the helios, which the kinematic factor pins to the body) PROVIDED eps_yaw stops acting on the odometry side — the config still has `MotionCalibApplyMask = -1`, and with it on, the yaw plant is absorbed into the odometry before the kinematic factor sees it, so the null arm passes and the yaw arm fails for reasons unrelated to the estimator.

## (1) Task 1 — the kinematic rows

**Task 1, Step 3: change** the model to the midpoint frame the code actually uses. With δ expressed at θ_mid = θ_n − ½dθ, R(θ_mid)ᵀ[R(θ_n) − R(θ_{n−1})]Δ = 2 sin(dθ/2)·JΔ, J = [[0, −1], [1, 0]], so

    δ_lat = −2 sin(dθ/2)·Δy + ψ·d_fwd,      δ_fwd = +2 sin(dθ/2)·Δx,      δ_θ: no mount term

(no (1−cos) columns; at the 0.8 rad single-correction limit they would be 0.30 — here per cycle they are 1e-3 and only add a meaningless regressor). ψ is the helios yaw as the localiser adds it to the heading (θ_est = θ_true + ψ); the sign is pinned by the table above. Relation to r1: eps_yaw = −ψ (kEps = −1), so the joint's helios-yaw column, if it is ψ, couples to the camera yaw with A = kCam = −1 DIRECTLY — do not divide by kEps again (the plan's "kCam/kEps with the helios yaw carried directly" would give +1 and flip the coupling). Pick one name for the column (ψ_h) and write the two constants next to it.

**Task 1, Step 1: change** the synthetic generator to the same midpoint model and add case E: arcs of one turning direction only (v/ω = 1 m) with a 1 % forward-scale error in the odometry — the lever must not come out confidently wrong (see Task 1b; this is the case the per-row EIV fails).

Weights and MA(1): using the learner's `last_m(a)` (× (1 − r)) as the row variance is right — χ²/dof 0.94–1.10 across runs — and the MA(1) needs no modelling for a MEAN regression: with smooth regressors the scan-white part telescopes, so the independent-row σ is CONSERVATIVE (every-second-row fits move by < 1σ and widen by √2, as expected). Keep every row at weight 1 (do NOT reuse the learner's `ma1_weight = 0.5`, which was for a variance regression), and say in the header that the reported σ is an upper bound.

**Task 5, Step 1: change** the wiring to pass `noise_innov_.last_m(0)` (forward) and `last_m(1)` (lateral) and `T.col(0)·delta` (forward), `T.col(1)·delta` (lateral) in the order `KinematicMount` expects; `odom_body[0]` is forward travel, `odom_body[2]` = dθ. Feed only when `fed` (consecutive scan-ok cycles, not searching), as the learner does.

**Unexplained and must be understood before Task 6 grades it:** Δx reads 19–27 mm for a 30 mm plant (Δy and ψ are fine). Not the scale confound (corr ≈ 0 with turns in both directions), not the frame (midpoint vs end differs by dθ³/24). Candidates: the scan-only pose is one GN step from the PREDICTED pose — during a pivot the prediction lags the scan optimum by dθ·|Δ| ≈ 1.5 mm/cycle, inside the linear range, so unlikely; the `mv·p_move·dt` term in m down-weighting pivot cycles asymmetrically; a residual eps_yaw/lever acting (check `yaw_offset()` in the log). A replay fit on pivot cycles alone (Δx = +20.8 ± 10.1) is too noisy to decide; add `odom_lat` to the log row check and fit CW and CCW pivots separately — a lever gives the same Δx for both, a timing/deskew effect flips sign.

## (1b) Odometry-readiness: shape of the marginalisation

**Which parameters couple.** For δ_fwd: −d_fwd·k_v (the only first-order term). For δ_lat: −d_lat·k_lat (≡ 0 on a differential base) and +d_fwd·eps_yaw (IDENTICAL to the ψ column — eps_yaw must not act or be in θ_o). Heading parameters (k_omega, b_omega, k_omega_w, dk_wheel) reach translation only through the midpoint integration, ≈ ½·d_fwd·dθ_err lateral, and through the regressor's own dθ (a 2 % scale on 2 sin(dθ/2)): both ≤ 1e-5 m per cycle — ignore. So J_o is one column (k_v on δ_fwd), two with k_lat.

**(1) is the right quantity, the wrong shape.** A per-row variance u'J_oΣ_oJ_o'u adds (d_fwd·σ_kv)² = (0.02 m × 0.02)² = (0.4 mm)² to rows of (4–6 mm)²: inert at the 2 % prior and inert at any plausible drift. The error it represents is not noise: the same Δk_v sits on every row and shifts Σ w·s·δ_fwd coherently. Its effect on the mount is Δx̂ − Δx = −Δk_v·Σ w s d_fwd / Σ w s² — zero when turns alternate (the logs: corr −0.00), −Δk_v·R_arc when they do not (1 % at 1.2 m = 12 mm). The exact marginalisation of a SHARED nuisance with prior Σ_o is the Schur complement:

    N = Σ w x xᵀ,  C = Σ w x J_oᵀ,  D = Σ w J_o J_oᵀ,   H_mount = N − C (D + Σ_o⁻¹)⁻¹ Cᵀ,   b likewise

— the Woodbury common-mode the project prescribes for correlated mask points, one level up. It is still DECOUPLED: θ_o is integrated out against the calibrator's posterior, never re-estimated, nothing acts. It does what the user asked by weight: with Σ_o at the prior and one-directional arcs it widens σ_Δx to ≈ R_arc·σ_kv = 24 mm; with Σ_o tight it costs nothing; with alternating turns C ≈ 0 and it is a no-op. **Task 1b, Step 1 (plan item 1): change** the per-row EIV to this common-mode form; `KinematicMount` stores N, C, D (3×1 and 1×1 for k_v) and takes Σ_o at `info()` time.

**(2) Σ_drift** goes into the same Σ_o (prior on the shared nuisance); it does not double count (1) — same nuisance, two sources of its uncertainty — nor the learner's m (per-row white vs shared). Define it as the exponentially weighted outer product of the change of the APPLIED θ_o per re-solve, in θ_o units; it is only meaningful inside the common-mode term, not per row.

**(3)** is not optional: with `apply_mask = -1` eps_yaw acts on the odometry (room_concept.cpp:8072 via `yaw_offset()`) and rotates every increment by ≈ −ψ before the kinematic factor sees δ. The 09-07-05 run (yaw-only plant) reads +0.61°, the lever runs +0.82/+0.92° for a 1.0° plant — consistent with a partially acting eps. Set `lidar_side_yaw = true` (exists) and keep eps out of θ_o; log `yaw_offset()` so the arms can prove it was 0.

**(4)** falls out of (1) done right: the stored C IS the cross-information, and `b_mount += C·Δθ_o` on an applied change is exact for the linear model. Needed whenever θ_o moves — (2) only widens, it does not correct the mean of rows accumulated under the old θ_o. Keep it; implement it from the same C (no second bookkeeping).

## (3) Task 3 — verticals

- **The helios planar rows are a double anchor — drop them.** The map walls were fitted by the SDF to this very scan (1.5–2.0 m band), so nᵀp_xy − d ≈ 0 for the helios by construction. With the "localiser's own covariance" (σ ≈ 10 mm, 0.16° — the solver's claim, 3–5x overconfident per the window memo) as the per-sweep nuisance prior, the Schur complement leaves the mount planar columns with information ≈ (10 mm)⁻² per sweep; over 10³ sweeps that is a 0.3 mm claim that dx = dy = dyaw = 0, and it out-votes the kinematic factor's 30 mm by 10⁴ in precision. **Task 3, Step 3: change** `VerticalMount` to carry (dx, dy, dyaw) rows only for the bpearl (relative to the helios), and give the per-sweep pose nuisance a WIDE prior (the pose-field σ: 0.05 m, 2°, or the published `res.covariance` after `PoseFieldPublish`, never the solver's marginal). **Task 3, Step 1: add** case E: helios planar rows with a planted 30 mm lever and a correct map → the vertical factor contributes zero information on helios (dx, dy, dyaw) (σ equals its prior).
- Tilt separability from the per-sweep planar nuisance: for the helios, q_z spans ≈ −0.55 … +1.5 m at 2 m range (fan +54.5/−15.5°, mount 1.1075 m in Shadow, ceiling ≈ 2.6 m), two-sided — a 0.5° tilt is an 18 mm differential across the span, well separated from a constant shift given ~10³ points per sweep. For the bpearl the wall span is one-sided (0 … 0.7 m) and tilt vs shift are nearly collinear; the plan rightly makes the floor the bpearl's tilt source — set the bpearl's vertical rows to walls-for-planar only, or its tilt σ from verticals will look informative when it is the prior pull.
- **The map is where the helios tilt put it.** A helios tilt ω_h displaces the band walls by (ω_hy·Δz, −ω_hx·Δz) with Δz = z_band − z_helios ≈ 1.75 − 1.1075 ≈ +0.65 m — a constant planar shift of the whole map relative to the true walls. For the helios's own rows the per-sweep nuisance absorbs it (that is one more reason the helios planar rows carry nothing). For the bpearl it is the same constant on every sweep and lands in the bpearl's relative (dx, dy): 8 mm per 0.7° of helios tilt. **Task 5, Step 1: add** coupling columns in `solve_mounts`: bpearl_rel_dx −= ω_hy·Δz, bpearl_rel_dy += ω_hx·Δz (sign fixed by the selftest: plant helios tilt, bpearl planar must stay at 0). Without it the helios-tilt arm moves the bpearl and "bpearl unaffected" fails for an unrelated reason.
- Ceiling: r = p_z − h_c + ω_x q_y − ω_y q_x + dz with h_c a session nuisance makes helios dz exactly unobservable from the ceiling ✓; the floor beyond 3.88 m (grazing) is the only absolute helios-z source and ROBOT_GEOMETRY records it varying 130–170 mm with where the robot stands — leave dz at the prior as the plan says, and make `joint_calib_report.py` print it as "prior" rather than a value. Note the consequence honestly: the helios–bpearl vertical offset is not calibrated by this plan; the cameras' heights are referenced to the floor via the triple point (G4), not to the helios, so nothing else inherits it.
- Circularity of "bpearl planar relative to the helios-built map": the map's planar frame IS the helios frame, so bpearl-relative = bpearl − helios ✓ (A = [I_b − I_h]) — sound, with the tilt coupling above and provided the bpearl sweep uses the pose at ITS stamp (the two sensors' sweeps are not simultaneous; a 50 ms offset at 0.4 m/s is 20 mm — a per-sweep planar nuisance with the WIDE prior absorbs it; the tight prior would not).

## (4) Gauges

Second-order cross-talk, acceptable: helios tilt → LiDAR corner xy at band height (8 mm) → camera pitch/height (≈ 0.15° at 3 m).

## (5) Task 6 — passing for the wrong reason / failing for another

1. `MotionCalibApplyMask = -1`: eps_yaw absorbs the yaw plant before the kinematic factor sees it (the 09-07 run already reads 0.61° of 1.0°). Set `lidar_side_yaw`/single owner and log `yaw_offset()` = 0 before any arm; otherwise the null arm passes trivially and the yaw arm fails.
2. The ψ row sign (section 1): a −ψ·d_fwd row returns −1° for a +1° plant and the signed grade fails a correct estimator.
3. The Δx shortfall (19–27 vs 30 mm, 2.5σ on 12-18-41) will fail "agrees within 2σ" on the lever arm as the estimator stands; understand it first (section 1), or the arm is graded on an unexplained bias.
4. Helios planar rows in the vertical factor (section 3): the lever arm reads ≈ 0 with a tiny σ — a confident wrong answer that "detects nothing" on the null arm and looks like a pass there.
5. Helios-tilt arm: the bpearl planar moves by ~8 mm through the map unless the coupling is modelled; "bpearl unaffected" fails for an unrelated reason.
6. Frames: `t_nom` in body (0.67/1.075) while points are in Shadow (0.7025/1.1075) biases the tilt scale by 5 % (bpearl) / 3 % (helios) — within the arm's σ for 0.7°, so it would PASS and be wrong; use one frame.
7. The bpearl injection is applied to the points after the RT transform in body axes about the sensor origin; if an implementer instead injects via the sensor-frame euler (Ry(π) nominal), roll and yaw come out sign-flipped against the grade (section 2).
8. `LidarMountInject*` are still 0.03/−0.02/1.0 in `etc/config.toml`: the null arm is not null until they are reset (the plan's "restore the r1 Task 6 config first" must include this file, which is uncommitted).
9. Grade rule: keep r1's three-part rule (informed, |est| > 2σ, |est − plant| < 2σ, signed); for the floor factor the σ will be tiny (10⁴ points, σ_flat 5 mm over a 3 m lever → 0.01° per 100 sweeps), so "agrees within 2σ" becomes a test of systematics (range bias, self-filter edge) rather than of the estimator — report the absolute error in mm/° too.
10. Evidence reset per arm must include the camera evidence files and `tmp/noise_innov` state only if the learner's m is reloaded from file (it is not — but the pose-field and the calibrator's `motion_calib_state.csv` are); write the reset list into Task 6.
