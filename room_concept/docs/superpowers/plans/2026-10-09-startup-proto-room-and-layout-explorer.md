# Basic Fleet: Start-up Proto-Room + Live Layout Explorer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Run the basic fleet (robot_concept, room_concept, controller, residual_concept) in room-ESTIMATION mode so that from the first second the room exists in the graph as a PROTO-ROOM (the same proto mechanism as a door crossing), the robot is driven by room_concept's planner through an `afford_room` affordance whose target is the next place to visit for layout estimation, and the proto-room is promoted IN PLACE (same node id, same frame) to a normal room when the layout becomes publishable.

**Why (state found 2026-10-09, read-only survey):** proto birth exists only on a door crossing and requires an existing room node (`room_scene_graph.cpp:802-812`); in Estimate mode nothing is published before `map_ready` (`room_scene_graph.cpp:237-273`); `afford_room` requires the room node (`dsr_update_affordance`, 1570) and its planner (`EpistemicPlanner`) plans POSE information against a known polygon; the layout explorers (`WallMap::frontiers`, the frontier/information-gain explorer, `RoomBoxesChannel::plan_path`) run only in `tools/wall_slam_selftest.cpp`; the controller resolves rooms with `rc::room::current_room_node`, which SKIPS protos, and stops without a ≥3-vertex `delimiting_polygon` (`controller_session.cpp:117-153`); residual binds once via `current_room` (skips protos) and never re-binds after its room is deleted. This is the deadlock recorded in memory (proto-room-for-estimation-time-navigation): the controller won't move without a room, the room won't converge without motion.

**Design decisions (taken here; flag in the report if the code contradicts one):**
1. **Start-up proto = `room_1` with a `proto` self-edge**, born in `initialize`/first localiser cycle when `estimating()` and no room exists. Frame = the robot's INITIAL pose, frozen for ever (gauge at t0); the estimator's one-shot re-anchor is absorbed into `T_room_proto_` exactly as the crossing path does (`take_pending_reanchor`). `dsr_room_id_` = the proto id from birth, so pose RT, walls, `afford_room` and later the polygon all target it.
2. **Its polygon is CONFIRMED FREE SPACE, never sensor range + margin** (memory design decision 2): the union of the LiDAR's free-space (visibility) polygons accumulated so far in the proto frame, eroded by the robot's body radius, simplified to ≤ 64 vertices, republished as it grows (throttled, ~1 Hz). The controller then plans inside space that has actually been seen to be free — safe by construction, because it cannot tell proto from surveyed. Run the door-aperture filter first if the existing helpers make that cheap (one open door would otherwise inflate it); if not, note it.
3. **Proto visibility (common/room_resolve/room_resolve.h):** keep rule 1 (`current` edge) and rule 2 (unique non-proto room); ADD rule 3: if there is no `current` edge and NO non-proto room, a UNIQUE proto room is the room. This lets controller and residual work with the start-up proto without ltsm, and changes nothing when a real room exists (door-crossing case: the old real room still wins until ltsm moves `current`). Rebuild every agent that includes the header (list them).
4. **Promotion at start-up is room_concept's call** (no identity question: it is the robot's first room; ltsm's identity authority concerns crossings). When the layout becomes publishable (`map_ready_` set at `room_concept.cpp:2814-2828`): write the learnt polygon (in the proto frame) as `delimiting_polygon`, delete the `proto` self-edge, keep the id and the frame. The door-crossing path keeps ltsm's promotion (unchanged); but fix the gap the survey found there too: after a crossing birth, `dsr_room_id_`'s polygon writer must target the proto, not the old room (or document why not and leave it).
5. **Live layout explorer → `afford_room` while estimating:** port the offline frontier/information-gain explorer from `tools/wall_slam_selftest.cpp` (`run_explore`, ~999-1105 and 1583-1738, on `WallMap::frontiers()`) into a live, pure class `src/layout_explorer.{h,cpp}` used by `RoomSceneGraph::dsr_update_affordance` when `estimating()` and the room is still proto. Same protocol (`rc::AffordanceManager{"afford_room"}`, epoch bump on re-proposal, completion/claim handling unchanged), parent = the proto id, target inside the proto's free-space polygon (reject/clip anything outside it — `controller_session.cpp:1069` marks targets outside the polygon `OutsideRoom`), yaw towards the frontier/worst-known wall. After promotion, hand back to the existing `EpistemicPlanner` (seed it with the promoted polygon — today it is seeded only once at room creation). Do NOT re-tune the explorer; port it as validated offline (docs: memory notes efe-objective-misfit-carries-it, resume-two-planner-bugs, bench-runs-the-agents-controller — the bench already runs the agent's controller).
6. **Publish before map_ready:** with a proto present, the robot→room RT and `afford_room` are published every cycle (today the 237-273 gate publishes nothing until map_ready). The room's WALL nodes stay unpublished until promotion.
7. **residual:** reset `room_node_id_` to 0 when its room node is deleted (`del_node_slot`), and re-resolve each `compute` while 0 (already the code path); re-initialise the grid extent from the polygon when the room changes or its polygon grows past the current extent (log it).
8. **Fleet launch:** a launcher config for the four agents + a corrected yakuake script:
   - `utils/fleet_basic.toml` (format of `utils/cognitive.toml`, for `utils/subcognitive.py`) with robot_concept `etc/config_shadow.toml`, room_concept `etc/config.toml`, controller `etc/config.toml`, residual_concept `etc/config.toml`.
   - fix `new_deployment.sh`'s "controller" tab (it `cd`s into viewer3d).
   - room_concept `etc/config.toml`: `[RoomShape] MapMode = "estimate"`, `[StartupProto] Enabled = true` (new section with the free-space polygon parameters), keep `BoxLayout = false`, `FreezeLayoutWhenPublishable` unchanged, `PreserveBootstrapRoom = false` (the start-up sweep must run BEFORE the proto is born).
   - Do not change controller behaviour beyond what decision 3 implies; if the controller needs a code change to plan in a growing polygon (grid rebuilt when the polygon changes?), find out from the code and make the minimal change, reported.

## Global Constraints
- Project rules in `active_inference/CLAUDE.md` (no thresholds where a model term works; `and/or/not`; C++23; `std::from_chars` / `imbue(classic)`; QueuedConnection only; SIGTERM never kill -9; `cbuild -j8` after `pgrep -a cc1plus`; no `-march=native`).
- Thread rules: `step_proto_room` runs on the LOCALISER thread; the wall map is localiser-only; anything the ingest/main thread needs goes as a copy (UpdateResult or a locked snapshot).
- Owned-node rules (CLAUDE.md "Stopping an agent", CONCEPT_AGENT_LIFECYCLE.md): the proto room, its RT and `afford_room` are room_concept's; startup sweep + graceful cleanup must remove them; `[Owns]` in controller's `etc/room_concept.toml` must still match (room_* subtree).
- No git commits by implementing agents. Live runs are the user's.

## Tasks
1. room_resolve rule 3 + its unit test (header-only test in a scratch harness or `common/room_resolve/` selftest): unique proto accepted only when no current edge and no non-proto room; existing behaviour pinned (current wins; a non-proto room beats a proto).
2. Free-space polygon accumulator (pure, `src/free_space_polygon.h`): visibility polygon per scan in the proto frame → union (raster or polygon clipping, whichever the codebase already has), erosion by body radius, simplification; selftest with a synthetic L-shaped room: grows monotonically, never contains unseen cells, never crosses a wall.
3. Start-up proto birth + promotion in room_concept (`room_scene_graph.cpp`): birth when estimating & no room; `dsr_room_id_` = proto; frozen frame; RT + polygon published before map_ready; promotion at map_ready (polygon = learnt layout in proto frame, delete `proto` edge, same id); door-crossing path untouched except the polygon-target gap. Log transitions to the existing `tmp/proto_room.csv` (one row per update, reason on every path).
4. Live layout explorer (`src/layout_explorer.{h,cpp}`) ported from the selftest + selftest of the port against the offline one on the same synthetic room (same targets for the same state); wired into `dsr_update_affordance` while estimating/proto; hand-back to EpistemicPlanner after promotion with the polygon re-seeded.
5. residual re-binding.
6. Fleet launcher + `new_deployment.sh` fix + config.
7. Build all touched agents (`cbuild -j8` each, one at a time); all selftests pass; report.

## Review Focus
1. A proto polygon that includes unseen space → controller drives into a wall (decision 2).
2. A gauge jump at promotion or at the estimator's re-anchor → every consumer teleports (decision 1).
3. Two rooms resolved at once (proto + leftover real room from a previous run) → startup sweep must precede birth; rule 3 must not fire with any non-proto room present.
4. `afford_room` target outside the proto polygon → `OutsideRoom` loop (offer, refuse, re-offer).
5. Residual stuck on a deleted room id.
